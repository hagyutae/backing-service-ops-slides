인스턴스 스펙 근거

Kafka 는 메시지를 JVM 힙에 담지 않고 디스크에 쓴 뒤 OS page cache 에서 읽습니다. 메모리는 힙이 아니라 page cache 로 쓰이고, 읽기와 쓰기가 모두 디스크 순차 처리량에 걸립니다.

항목내용
Standard_D2ds_v5
2 vCPU / 8 GiB		메모리 최적화 계열이 아니라 범용 계열의 최소 크기
OS 와 exporter약 1 GiB
JVM 힙2 GiB. 힙을 늘리면 page cache 가 줄어 읽기가 디스크로 내려감
page cache약 5 GiB. segment 파일을 sendfile 로 소켓에 바로 내보내는 데 씀
데이터 디스크128 GiB · 3,000 IOPS · 125 MB/s. segment 가 쌓이는 곳

Key 기반 Partitioning

  • Kafka 메시지는 Key 와 Payload, Timestamp, Headers 로 구성
  • Kafka 메시지의 Key 는 Partitioner 내에서 해시 함수를 통해서 Partition 을 배정받음
  • 같은 Key 를 가지는 메시지는 같은 Partition 에 배정되는 것이 보장됨. 따라서 같은 Key 를 가지는 메시지의 처리 순서는 발행된 순서에 따르는 것이 보장됨
  • Key 가 없는 메시지들은 Partition 들에 고르게 흩어져서 전달됨

Consumer Group

하나의 Topic 을 여러 Consumer 가 나눠 처리하면서도 같은 메시지를 중복해서 읽지 않으려면, 어느 Consumer 가 어느 Partition 을 맡을지 정해 주는 단위가 필요합니다. 그 단위가 Consumer Group 입니다.

  • Partition 1개는 Consumer 1개에 의해서만 소비됨
  • Group 간의 Partition 소비는 독립적임
group.id 가 같으면 나눠 읽고, 다르면 각자 다 읽습니다.
같은 메시지 스트림을 서로 다른 애플리케이션이 소비할 때, 애플리케이션별로 그룹을 나눕니다.

Rebalance

Rebalance 는 그룹 안의 Consumer 들에게 Partition 을 다시 나눠 주는 것입니다.
멤버가 바뀌면 누가 어느 Partition 을 맡을지 처음부터 다시 정합니다.

  • 트리거: Consumer Group 내 Consumer 멤버 추가·이탈, Partition 수 변경
  • 부작용: Rebalance 로 인한 Partition 재할당이 끝날 때까지 처리 멈춤
Rebalance 가 잦으면 처리가 밀리게 되므로 최소화해야 합니다.

KRaft 의 정의와 역할

KRaft 는 Kafka Raft 입니다. Raft 는 여러 노드가 하나의 값에 합의하는 알고리즘이고, KRaft 는 그것을 Kafka 자신의 로그 위에 구현한 것입니다.

  • 선출: controller 들이 투표해 leader 하나를 뽑음
  • 직렬화: leader 만 씀. Offset 이 변경의 순서를 정함
  • 저장: 로그의 이름은 __cluster_metadata. Topic 목록, Partition 배치, Broker 목록이 담김
  • 전파: Broker 는 leader 에게서 로그를 Fetch 로 당겨 읽어 자기 캐시를 채움
controller follower 는 가용성을 위한 것이고, 실제 요청 처리에 쓰이는 것은 Broker 의 메타데이터 캐시입니다.
follower 는 투표에 참여하는 voter 이며, leader 가 정지하면 그중 하나가 역할을 이어받습니다. Broker 는 투표하지 않는 observer 로, leader 에게서 같은 로그를 받아 어느 Partition 이 어디에 있는지를 파악합니다.
