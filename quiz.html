각 문항에서 가장 알맞은 것 하나를 고르세요. Redis 2문항, MongoDB 2문항, Kafka 2문항, 장애대응 · 모니터링 4문항입니다.

1Redis 운영

AOF 를 켠 Redis 에서 appendfsync 를 기본값으로 두었습니다. 프로세스가 갑자기 종료됐을 때 잃을 수 있는 쓰기의 최대 구간은 무엇입니까.

  1. 없음. 모든 쓰기가 디스크에 기록된 뒤 응답하므로 손실이 발생하지 않음
  2. 최대 1초 분량의 쓰기
  3. 마지막 RDB 스냅샷 이후에 들어온 모든 쓰기
  4. OS 가 내보내는 시점에 달려 있어 손실 구간을 예측할 수 없음
2Redis 운영

Sentinel 을 3대로 구성하는 이유로 옳은 것은 무엇입니까.

  1. master 와 replica 각각에 하나씩 붙어야 하므로
  2. 1대가 정지해도 남은 2대가 quorum 2 와 리더 선출의 과반 2 를 모두 채울 수 있으므로
  3. Sentinel 이 데이터를 3중으로 복제해 보관하므로
  4. Redis 가 Sentinel 대수를 홀수로만 허용하므로
3MongoDB 운영

질의 성능을 점검하려고 explain("executionStats") 를 실행했더니 실행 단계에 COLLSCAN 이 나왔습니다. 무엇을 뜻합니까.

  1. 인덱스를 탐색해 문서를 찾은 상태
  2. 인덱스를 쓰지 않고 컬렉션 전체를 읽은 상태
  3. 인덱스만으로 결과를 만들어 문서를 한 건도 읽지 않은 상태
  4. 조회 결과를 메모리에서 다시 정렬한 상태
4MongoDB 운영

데이터 멤버 3개(PRIMARY 1대, SECONDARY 2대)로 구성한 Replica Set 에서 PRIMARY 노드가 정지했습니다. 무엇이 일어납니까.

  1. 남은 SECONDARY 2대가 과반을 이뤄 그중 하나를 새 PRIMARY 로 선출
  2. 남은 멤버가 과반에 못 미쳐 선출이 일어나지 않고 읽기만 유지
  3. SECONDARY 2대가 모두 쓰기를 받기 시작해 양쪽에 쓸 수 있게 됨
  4. 운영자가 수동으로 승격시키기 전까지 아무 일도 일어나지 않음
5Kafka 운영

replication factor 가 3 이고 min.insync.replicas 가 2 인 Topic 에 acks=all 로 produce 하고 있습니다. Broker 1대가 정지하면 어떻게 됩니까.

  1. ISR 이 2로 남아 produce 가 계속 성공
  2. ISR 이 줄었으므로 produce 가 즉시 실패
  3. 정지한 Broker 가 복구될 때까지 대기했다가 성공
  4. leader 만 살아 있으면 되므로 min.insync.replicas 와 무관하게 성공
6Kafka 운영

Partition 이 3개인 Topic 을 Consumer Group 하나가 읽고 있습니다. 처리량을 늘리려고 Consumer 를 5개로 늘리면 어떻게 됩니까.

  1. 5개가 Partition 을 나눠 맡아 처리량이 늘어남
  2. 3개만 Partition 을 할당받고 나머지 2개는 유휴 상태가 됨
  3. Partition 이 자동으로 5개로 늘어나 균등하게 배분됨
  4. 할당받지 못한 Consumer 때문에 Consumer Group 이 오류로 중단됨
7장애대응 · 모니터링

Consumer Lag 이 늘어난 것을 확인했습니다. 원인 후보를 절반으로 줄이기 위해 가장 먼저 볼 것은 무엇입니까.

  1. Consumer 노드의 CPU 사용률
  2. Partition 별 Lag 이 고르게 늘었는지 한쪽에 몰렸는지
  3. Broker 노드의 디스크 사용률
  4. Producer 의 전송 실패 로그
8장애대응 · 모니터링

Redis 지표를 보다가 evicted_keys 가 계속 늘고 있는 것을 발견했습니다. 어떻게 읽어야 합니까.

  1. TTL 이 만료돼 사라진 키의 수이므로 설계대로 도는 정상 동작
  2. 메모리가 모자라 키가 축출되고 있는 것이므로 조치가 필요한 상태
  3. 복제가 끊겨 replica 에서 사라진 키의 수
  4. 클라이언트가 DEL 로 지운 키의 누적 수
9장애대응 · 모니터링

Kafka Broker 에서 메모리 압박이 관측됐습니다. JVM 힙을 크게 늘리는 대응이 적절하지 않은 이유는 무엇입니까.

  1. 힙이 커지면 GC 가 동작하지 않게 되므로
  2. 힙이 커진 만큼 page cache 가 줄어 읽기가 디스크로 내려가므로
  3. Kafka 는 힙 크기를 바꾸는 설정을 제공하지 않으므로
  4. 힙을 늘리면 Partition 수가 자동으로 줄어들므로
10장애대응 · 모니터링

MongoDB Replica Set 에서 SECONDARY 하나의 복제 지연이 계속 벌어지고 있습니다. 그 노드의 CPU 와 디스크 IO 를 확인했더니 오히려 낮았습니다. 무엇을 의심해야 합니까.

  1. 부하가 낮으므로 지연이 곧 저절로 해소되는 상태
  2. 따라가지 못하는 것이 아니라 그 노드의 mongod 프로세스가 정상 동작하지 않는 상태
  3. PRIMARY 의 인덱스가 빠져 조회가 느려진 상태
  4. oplog 윈도우가 넓어져 지연이 실제보다 크게 보이는 상태
